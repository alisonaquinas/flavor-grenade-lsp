# Reject Non-File LSP URIs Before Path Handling

> [!INFO] `BUG-016` · Bug · Phase 18 · Severity: `high` · Priority: `high` · Status: `open`

## Summary

`initialize`, `initialized`, and several text-document request paths accept URI
strings without a shared `file://` allowlist, so non-file schemes can reach
path conversion or resolver logic instead of returning InvalidParams.

---

## Reproduction Steps

1. Send `initialize` with `rootUri: "https://example.invalid/vault"`.
2. Send `initialized`.
3. Observe that lifecycle path handling proceeds through `SingleFileModeGuard.uriToPath()` rather than a protocol error.

**Minimal reproducing vault content:**

```markdown
# Alpha
```

**LSP method / trigger:** `initialize`, `initialized`, and text document requests with `textDocument.uri`

---

## Expected Behaviour

Non-`file://` URIs are rejected with JSON-RPC InvalidParams before reaching any
path or resolver code.

---

## Actual Behaviour

`InitializeHandler` stores the URI string as-is, and
`SingleFileModeGuard.uriToPath()` converts or returns arbitrary URI strings.

---

## Proposed Fix

Add a shared URI validator that parses with `new URL()`, requires
`protocol === "file:"`, and throws `JsonRpcError(InvalidParams, ...)` from all
request paths that accept client-provided document, root, or file-operation
URIs.
