# Block Command-Start Server Spawn In Unsupported Extension Environments

> [!INFO] `BUG-025` · Bug · Phase 18 · Severity: `high` · Priority: `high` · Status: `open`

## Summary

The extension's automatic startup path blocks server spawn in Restricted Mode
and virtual workspaces, but command-triggered startup can bypass that disabled
environment check and call `startLanguageClient()`.

---

## Reproduction Steps

1. Activate the extension in an environment where `describeWorkspaceEnvironment()`
   returns `canStartServer: false` (Restricted Mode or a virtual workspace).
2. Invoke a command that calls the `LanguageClientProvider`, such as
   `flavorGrenade.rebuildIndex`, `flavorGrenade.restartServer`, or
   `flavorGrenade.showOutput`.
3. Observe that `startClient(commandId)` runs command startup checks and then
   calls `startLanguageClient(context)` without rechecking `getDisabledStatus()`.

**Minimal reproducing vault content:**

```markdown
N/A - extension command lifecycle issue.
```

**LSP method / trigger:** VS Code command invocation.

---

## Expected Behaviour

Unsupported extension environments must remain disabled regardless of whether
startup is triggered automatically or by an explicit command. Commands may show
status or troubleshooting information, but must not spawn the language server
when the workspace is untrusted or virtual.

---

## Actual Behaviour

`maybeStartClient()` checks `getDisabledStatus(context)` before starting the
server, but `startClient(commandId)` only calls `decideStartupGate()` for command
activation and then starts the language client. `decideStartupGate()` currently
returns `startClient: true` for command triggers.

## Proposed Fix

Move the disabled-environment guard into the shared `startClient()` path before
`startLanguageClient(context)` is called. Command handlers that only need status
or troubleshooting information should still work without creating a
`LanguageClient`.
