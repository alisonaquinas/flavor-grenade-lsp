# Bound Parser Runtime And ReDoS Exposure

> [!INFO] `BUG-018` · Bug · Phase 18 · Severity: `high` · Priority: `high` · Status: `in-review`

## Summary

The parser has no enforced per-file timeout and no adversarial regression suite
for regex-heavy token parsers, leaving `Security.Parser.ParseTimeout` and
`Security.Parser.ReDoS` without evidence.

---

## Reproduction Steps

1. Create a large Markdown file with many unmatched link, code, math, and comment delimiters.
2. Trigger initial vault scan or `textDocument/didOpen`.
3. Observe that parser work is unbounded by a documented timeout policy.

**Minimal reproducing vault content:**

```markdown
[[[[[[[[[[[[[[[[[[[[[[[[[[[[[[[[[[[[[[[[[[[[[
```

**LSP method / trigger:** initial vault scan, `textDocument/didOpen`

---

## Expected Behaviour

Any single vault file that exceeds the parser budget is skipped or returns empty
results without crashing or blocking the server indefinitely.

---

## Actual Behaviour

`OFMParser.parse()` calls each parser synchronously with no timer or
adversarial performance guard.

---

## Proposed Fix

Introduce a parser budget service or injectable clock for tests, add
adversarial fixtures for every token parser, and document any regex rewrite
needed to keep worst-case behavior bounded.
